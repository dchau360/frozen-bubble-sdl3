A bare `CREATE` (no blob) behaves exactly as before: no `OPTIONS:` push at all, server defaults apply. Client-side, `NetworkClient::SendOptions()` was split into a reusable `BuildOptionsBlob()` (the blob-construction logic, now callable without also sending it) plus a thin `SendOptions()` wrapper that calls it and sends `SETOPTIONS <blob>` -- this let the tournament panel build the same blob for `TOUR CREATE` without duplicating the snprintf logic. - **"The tournament had some disconnection issues" -- root-caused and fixed (2026-09-11, later same day).** The user saw 2 of 4 players leave immediately when starting a tournament, a 3rd leave after one round, then "winning one round forces the loser to forfeit the rest of the tournament," and finally confirmed a live retry still lost *all four* connections. `server-verbose.log` (foreground debug server, `-d -o DEBUG`) caught it red-handed: every drop was `[fd] <garbage> -> MISSING_FB_PROTOCOL_TAG` immediately followed by `conn_terminated`, where `<garbage>` was actually a well-formed in-game `GAMEMSG` (e.g. `BFdchau3` = player-id byte `'B'` + win-claim `"Fdchau3"`, `AS7:0:0:19:0:0` = a round-stats sync) landing on a connection that had just been knocked out of "prio"/binary-protocol mode. Two compounding bugs, both fixed:
  1. **Root cause: `victoriesLimit` mismatch between client and server for tournament matches.** `server/tournament.c`'s bracket already implements its own best-of-three *across separate rooms* -- `commit_result()` tears the current room down (`game_tournament_retire()` → `remove_prio()` for both players) the instant both sides' `TOUR REPORT` land, whether the match is decided or not, then waits for both to ready up again before `game_tournament_start()` creates a *fresh* room for the next round. But `src/mainmenu_tournament.cpp`'s `CFG_CONFIRM` handler hardcoded `victoriesLimit=5` in the ruleset blob sent to every tournament room, telling the *client* to keep playing up to 5 rounds inside that one room before the match was "over." The client's own round-end code (`ReportTournamentResult()`, `src/bubblegame_state.cpp`) reports every single round's result unconditionally (not gated on the client's local `gameMatchOver`), so after round 1 the server already considered the match's current room finished and retired it -- while the client, still mid-session for what it thought was a 5-round match, went on sending ordinary in-game bytes (win-claim `F`, stats-sync `S`, ...) into a room the server had just destroyed and a connection just demoted out of prio. Every single one of those stray bytes fatally violated `process_msg`'s "must start with FB/" check, killing the connection outright -- which the tournament coordinator then read as a dropped/withdrawn player and awarded the match to the opponent by forfeit. This is what "immediately left," "left after one round," and "winning one round forces forfeit" all actually were: not real disconnects or real forfeits, just this race, and it compounded across every match in the bracket until only one player was left standing (observed literally: a `champion` by forfeit chain, all three others `withdrawn`). **Fix:** changed the hardcoded ruleset value to `victoriesLimit=1` (`src/mainmenu_tournament.cpp`) -- one room now equals exactly one round, matching the server's actual unit of play, so a tournament match's local session and the coordinator's bracket state boundary always land on the same round.
  2. **Defense in depth: the server no longer treats an orphaned in-game byte as fatal.** Even with (1) fixed, a client's trailing in-game protocol chatter around a round boundary can still theoretically race the coordinator's retire. `process_msg`'s "missing FB/ tag" check (`server/game.c`) now only closes the connection when `find_game_by_fd(fd)` still finds a room for it; a non-FB/-prefixed line arriving with no current room is logged at DEBUG and silently dropped instead, since that shape (an in-game byte with nowhere to route it) is a structurally-expected side effect of one-room-per-bracket-round, not a hostile or broken client.
  3. **Unrelated but discovered along the way and also fixed: `conn_recently_active()`'s NICK-collision window was too tight.** `server/net.c` judged a same-nick connection "live" only if it had sent something in the last 2 seconds, against a lobby `LIST` poll interval of 500ms on a *whole-second-truncated* clock -- a margin thin enough that ordinary jitter (screen transitions, several app instances launched close together) could misjudge a genuinely live connection as a stale ghost and silently `conn_terminated()` it while handing its nickname to the newcomer. Widened to 10 seconds; real ghost cleanup on an actual reconnect is unaffected since a person takes far longer than that to notice a drop and relaunch. `tests/server_discordalert_test.py`'s `test_reconnect_replacing_a_ghost_does_not_re_announce` (which depends on this exact window) was updated to match (`time.sleep(10.5)`).
  All three changes verified together: full `ctest` 35/35 passed (2 skipped by design), including `server-tournament-test`'s best-of-three coverage and the discord-alert ghost-eviction test at the new window.
- **"chain reaction wasn't working" -- root-caused and fixed (2026-09-11, second pass).** The first pass traced the ruleset-plumbing all the way up to `chainReaction = chainReactionEnabled` correctly copying the net-synced value into the gameplay flag right as a network game transitions from lobby to `BubbleGame`, and found nothing wrong -- but stopped one step too early. `MainMenu::SetupNewGame()`'s case 4 (network multiplayer) runs immediately after that copy, and its tournament branch (added in `7b947f25`, back when the "Configure ruleset" screen didn't exist yet) unconditionally stomped the just-copied value back out: `ns.gameMode = GameMode::Classic; ns.chainReaction = false;` plus `ns.playerColors[i] = 8; ns.aimGuide[i] = false;` for every slot, regardless of what the organizer had actually picked on the CFG_MODE/CFG_CHAIN/CFG_COLORS/CFG_AIM toggles (screen added later in the same feature but this override was never revisited). Net effect: **four of the tournament creation screen's five ruleset toggles were completely inert** -- Game Mode, Chain Reaction, Aim Guide and Colors all reached the server fine (visible in `OPTIONS:` on the wire, per the first pass's trace) and were even echoed back correctly into `netGameMode`/`chainReactionEnabled`/`playerColorCounts`/`playerAimGuide`, but every actual tournament match still played Classic/no-chain/8-colors/no-aim no matter what was configured. Only Attack Mode happened to survive, because it's the one field that block never touched. **Fix** (`src/mainmenu.cpp`, `SetupNewGame` case 4): removed the `gameMode`/`chainReaction`/`playerColors`/`aimGuide` overrides, keeping only the genuinely structural ones a tournament match actually requires and that have no corresponding toggle -- `victoriesLimit=0` (the tournament coordinator, not the client, owns the first-to-two score; see the `victoriesLimit=1` comment at `TOUR CREATE`'s `BuildOptionsBlob` call in `mainmenu_tournament.cpp`), `mouseEnabled=true`, and `playerTeams[i]=0` (always exactly two individual entrants, no team assignment UI in tournament creation). Verified against `menu-touch-gesture-test` and `server-tournament-test` (both still pass) and a local release build. Known follow-up, not fixed here: the registration screen's static label ("Classic · 8 colors · Compression on · Aim guide off" in `TournamentPanelRender()`) is now stale for a tournament created with a non-default ruleset -- fixing it needs the server to actually put the ruleset in the tournament listing/snapshot push (`TournamentListing`/`TournamentSnapshot` in `src/tournamentstate.h` carry none of it today), which is a wire-protocol change, not a one-line label fix.

**The server review requested in item 4 (disconnect ordering, expired-tournament cleanup, command parsing, tournament ID wrap) has been completed as a traced static review; no defects found, no code changed.** Findings, one per sub-area:
- *Disconnect ordering.* Traced a full tournament-participant disconnect end to end: `conn_terminated()` (`server/net.c`) closes the socket and frees `nick[fd]` to `NULL` *before* calling `player_part_game(fd)` then `player_disconnects(fd)`. `player_part_game_()`'s tournament branch (`src/`→ `server/game.c:1543-1548`, its own comment already documents this) uses that cleared `nick[fd]` to route a real disconnect to `tournament_disconnect()` rather than `tournament_withdraw()` — the latter is reserved for a live `PART` where the entrant might reconnect. `tournament_disconnect()` → `tournament_withdraw()` → `leave()` → `forfeit()` → `retire()` → `game_tournament_retire()` runs *before* `player_part_game_()` reaches its own `find_game_by_fd(fd)`, so by the time that runs the reserved room is already gone and `g` is correctly `NULL` — no double teardown. `player_disconnects()` (`server/game.c:708`) then calls `tournament_disconnect()` a second time, unconditionally; this looked like a redundant double-dispatch at first, but it isn't: `player_part_game_()` only reaches the tournament branch when `tournament_active(fd)` was already true, so a disconnecting fd with no tournament involvement (or one already eliminated) skips that branch entirely, and only `player_disconnects()`'s unconditional call clears `connected[fd]`/`watched[fd]` for it. Skipping that clear would leave a stale `watched[fd]` pointing at a live tournament after the socket closes, and a later `broadcast()` would try to `push()` a snapshot down a closed fd. When both calls *do* fire (fd was tournament-active), the second is a cheap no-op: the first call already set `e->fd = -1`, so `self()` finds no match. The socket-close-vs-broadcast race is also closed: `tournament_disconnect()` sets `connected[fd] = 0` as its first line, before any `leave()`-triggered `broadcast()` can run, and `broadcast()` gates every `push()` on `connected[fd]`.
- *Expired-tournament cleanup.* `tournament_tick()`'s retirement branch (`t->state >= COMPLETE && now >= t->expires`) clears every fd's `watched[fd] == t->id` match *before* `memset(t, 0, sizeof(*t))` zeroes `t->id` — ordering matters here since the comparison is against the pre-zero value, and it's correctly sequenced. A freed slot's `id` reads back `0`, `find()` explicitly excludes `id == 0`, so a stale client reference to an expired tournament ID gets a clean `NOT_FOUND` rather than colliding with whatever tournament later reuses that array slot.
- *Command parsing.* `tokens[6]`/`values[4]` bounds are enforced before use (`argc` capped at 5 tokens including the op, `values[i-1]` only written for `i` in `[1,argc)`). The `READY` op's fixed `expected == 4` (op + 3 numeric args) initially looked wrong for the registration-phase `READY <tid>` case until cross-checking `docs/TOURNAMENT_PROTOCOL.md`: the wire format always sends `READY <tid> <mid> <round>`, with `mid`/`round` as literal `0 0` placeholders during registration, and the handler's `values[1] || values[2]` check matches that. `t->bracket[values[1]-1]` is only indexed after `values[1] <= 0 || values[1] > t->matches` is checked. `strcpy(e->name, nick[fd])` into `char name[11]` is safe because `is_nick_ok()` rejects any nick over 10 characters before it can ever reach `nick[fd]`.
- *Tournament ID wrap.* Both `next_tid` (tournament IDs) and each tournament's own `next_pid` (entrant IDs, which keep incrementing across REGISTRATION-phase join/leave churn even though live `count` stays capped at `ENTRANT_LIMIT`) are guarded by an explicit `== INT_MAX` check before the value is ever used and incremented, so neither can wrap — the failure mode at exhaustion is a hard `LIMIT_REACHED`/`FULL` reply, not reuse or overflow. Not practically reachable (would need on the order of 2^31 tournaments or joins against one process's uptime).
